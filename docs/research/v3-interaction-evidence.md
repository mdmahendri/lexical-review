# Version 3 interaction evidence baseline

Status: Research snapshot for the version 3 planning map, 2026-08-25

Question: What primary-source interaction evidence should constrain the version 3 contract for insertion, deletion, atomic replacement, core inline formatting, paragraph split, paragraph merge, and selective resolution across typing, commands, selections, keyboard shortcuts, clipboard, IME, and browser input routes?

## Executive answer

The evidence supports one strong product boundary: version 3 should define proposal semantics at Lexical's command/model layer, not attach semantics to particular keys or DOM events. Keyboard shortcuts, toolbar actions, browser `beforeinput`, clipboard events, IME reconciliation, and a future programmatic/AI API are different routes to the same editing intentions. Input Events deliberately describes intentions expressed through keyboard, IME, speech, and similar mechanisms, while Lexical 0.49 already translates browser-specific routes into commands such as controlled insertion, deletion, paragraph insertion, formatting, removal, and paste. ([Input Events Level 2, definitions and input types](https://www.w3.org/TR/2026/WD-input-events-2-20260501/#interface-InputEvent-Attributes); [Lexical event routing at v0.49.0](https://github.com/facebook/lexical/blob/v0.49.0/packages/lexical/src/LexicalEvents.ts#L815-L1180); [Lexical keyboard routing at v0.49.0](https://github.com/facebook/lexical/blob/v0.49.0/packages/lexical/src/LexicalEvents.ts#L1605-L1655))

Across Word, Google Docs, CKEditor, and ONLYOFFICE, stable product-level patterns are narrower than a complete interaction standard:

- editing while tracking is enabled creates visible pending changes rather than immediately replacing the accepted/original projection;
- insertions, deletions, and formatting are distinguishable;
- reviewers can resolve an individual change and commonly all changes, and can navigate between changes;
- products expose accepted/final and rejected/original projections without necessarily resolving the pending changes; and
- authors can continue editing while pending changes exist. ([Microsoft Word track changes](https://support.microsoft.com/en-us/word/training/track-changes-in-word); [Google Docs suggesting](https://support.google.com/docs/answer/6033474); [CKEditor track changes](https://ckeditor.com/docs/ckeditor5/latest/features/collaboration/track-changes/track-changes.html); [ONLYOFFICE review mode](https://helpcenter.onlyoffice.com/docs/userguides/document_editor/Review.aspx))

The vendors do **not** establish one contract for proposal grouping, replacement atomicity, editing one's own pending insertion, clipboard projections, or paragraph-boundary grouping. Those are product decisions. Where Web Editor Revisions v1 already defines a result, version 3 should follow it; where ordinary editing cannot be represented by v1, version 3 must refuse the gesture predictably or first feed a reproducible adoption finding back to the standard. It must not invent a locally convenient interpretation and call it conforming. ([Web Editor Revisions v1 scope and proposal kinds](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L40-L77); [v1 selective resolution](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L262-L280))

Three adoption gaps are release-shaping:

1. **Drafting versus immutable proposal identity.** Editors let an author extend, split, update, or delete their pending work. CKEditor, for example, auto-expands adjacent suggestions, updates suggestion data, and directly folds formatting into the author's insertion by default. ONLYOFFICE exposes deletion of the reviewer's own change. Web Editor Revisions v1 instead makes a proposal's target, kind, and payload immutable under one identity and excludes withdrawal/cancellation. Version 3 needs an explicit authoring-session layer or a standard amendment before it can claim that all such interactions are v1-native. ([CKEditor suggestion granularity](https://ckeditor.com/docs/ckeditor5/latest/features/collaboration/track-changes/track-changes-granular-suggestions.html); [CKEditor formatting policy](https://ckeditor.com/docs/ckeditor5/latest/api/module_track-changes_trackchangesconfig-TrackChangesConfig.html#member-trackFormatChanges); [ONLYOFFICE review mode](https://helpcenter.onlyoffice.com/docs/userguides/document_editor/Review.aspx); [v1 immutable identity](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L169-L181); [v1 excluded withdrawal](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L60-L75))
2. **Compound multi-paragraph gestures.** A cross-paragraph replacement, cross-paragraph delete, multiline paste, or Enter over a non-collapsed selection naturally combines text changes with paragraph splits/merges. V1 permits only paragraph-local text ranges and excludes dependent proposals. The common gesture therefore cannot be truthfully encoded as one v1 proposal or as independently resolvable child proposals. ([v1 target types](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L153-L167); [v1 compatibility restriction](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L262-L280); [Lexical paragraph insertion](https://github.com/facebook/lexical/blob/v0.49.0/packages/lexical/src/LexicalSelection.ts#L1355-L1393))
3. **IME is a provisional browser mutation, not a stream of proposals.** `insertCompositionText` is non-cancelable; the active passage is repeatedly replaced during composition. Lexical deliberately lets the browser mutate during composition and reconciles the committed state, with platform-specific paths for Android, iOS Korean input, Safari, and Firefox. Version 3 should publish at most one proposal for the committed composition intent, not one per composition update. ([Input Events composition order](https://www.w3.org/TR/2026/WD-input-events-2-20260501/#input-event-order-during-composition); [Lexical composition handling](https://github.com/facebook/lexical/blob/v0.49.0/packages/lexical/src/LexicalEvents.ts#L815-L977); [Lexical input reconciliation](https://github.com/facebook/lexical/blob/v0.49.0/packages/lexical/src/LexicalEvents.ts#L1230-L1330))

## Source and version boundary

This is interaction evidence, not an adoption census or usability study. It uses primary sources owned by the standards bodies, products, or source repositories concerned.

### Web Editor Revisions

The sibling publication at commit [`e6ac892`](https://github.com/mahendrimd/web-editor-revisions/tree/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1) is treated as the portable semantic baseline. It intentionally does not standardize UI, DOM shape, browser APIs, runtime structures, or workflow policy. It includes six proposal kinds, four Boolean inline formats, selective resolution, exact projections, and remapping; it excludes proposal withdrawal, overlapping/nested/dependent proposals, undo/redo, permissions, and richer structure. ([v1 purpose and scope](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L9-L22); [v1 included and excluded surfaces](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L40-L77))

### Lexical

`lexical-review` declares `lexical`, `@lexical/react`, `@lexical/clipboard`, and `@lexical/utils` peers as `>=0.45.0 <0.50.0`, while its development graph and lockfile pin the relevant packages to `0.49.0`. ([package manifest at the researched commit](https://github.com/mahendrimd/lexical-review/blob/56981eb3a52b33a38eeaae48763fa49aecc6ec03/packages/lexical-review/package.json#L49-L62))

Exact-source inspection used the detached upstream tag `v0.49.0`, commit `ffe90924bd55b5d450c88de0f9f1c8b228c4a221`, from `https://github.com/facebook/lexical.git`. The manifest and lockfile agree on 0.49.0. The isolated research worktree has no installed dependency graph; therefore no claim in this note depends on an unverified local package installation.

### Vendor observation boundary

- **CKEditor:** current first-party Track Changes documentation and API pages, with behavior that is also inside the sibling standard's pinned Reference Web Editor v48.3.1 profile. Its examples show separate insertion and deletion suggestions for replacement, configurable suggestion joining, command-backed formatting, selection/all resolution commands, and configurable clipboard treatment. ([overview](https://ckeditor.com/docs/ckeditor5/latest/features/collaboration/track-changes/track-changes.html); [granularity](https://ckeditor.com/docs/ckeditor5/latest/features/collaboration/track-changes/track-changes-granular-suggestions.html); [TrackChanges API](https://ckeditor.com/docs/ckeditor5/latest/api/module_track-changes_trackchanges-TrackChanges.html))
- **Google Docs:** first-party end-user help and Docs API documentation. The help contract covers addition, deletion, replacement, individual/all resolution, keyboard navigation, and preview. The API exposes suggestion identifiers on inserted/deleted runs and separate suggested style changes. It does not document detailed caret, paragraph-boundary, clipboard, or IME behavior. ([suggesting help](https://support.google.com/docs/answer/6033474); [screen-reader review workflow](https://support.google.com/docs/answer/6239410); [suggestions API](https://developers.google.com/workspace/docs/api/how-tos/suggestions))
- **Microsoft Word:** first-party support documentation plus Microsoft's WordprocessingML explanation. The product exposes insertion, deletion, and formatting markup, individual/all resolution and projection views. The file-model explanation establishes that deleting a paragraph mark merges the adjacent paragraphs without also marking all their text deleted. It does not prove one cross-platform Word interaction contract for keys, grouping, clipboard, or IME. ([Word track changes](https://support.microsoft.com/en-us/word/training/track-changes-in-word); [tracked paragraph-mark deletion](https://learn.microsoft.com/en-us/office/open-xml/word/how-to-accept-all-revisions-in-a-word-processing-document#del-deleted-paragraph))
- **ONLYOFFICE:** first-party review documentation. It exposes individual/all resolution, final/original projection previews, editing in markup modes, and deletion of the reviewer's own changes; its AI feature can insert generated output through Track Changes for ordinary accept/reject review. ([reviewing documents](https://helpcenter.onlyoffice.com/docs/userguides/document_editor/Review.aspx); [AI output “as review”](https://helpcenter.onlyoffice.com/ai/userguides/ai-in-the-document-editor.aspx))

## Lexical-imposed boundaries

### One intent has multiple browser routes

Input Events says input types represent the user's editing intention and that the physical expression can be keyboard, IME, speech, or another platform-specific method. It also warns that browsers need not support every input type. ([Input Events, definitions and input-type table](https://www.w3.org/TR/2026/WD-input-events-2-20260501/#interface-InputEvent-Attributes))

Lexical 0.49 reflects that reality:

- `beforeinput` routes text, replacement, drop, paste, paragraph, deletion, formatting, undo, and redo to Lexical commands; ([Lexical `beforeinput` switch](https://github.com/facebook/lexical/blob/v0.49.0/packages/lexical/src/LexicalEvents.ts#L1018-L1188))
- keyboard handlers independently route Enter, Backspace/Delete, word/line deletion, and bold/italic/underline shortcuts to those commands, while deferring to `beforeinput` on specific iOS/Safari paths; ([Lexical key routing](https://github.com/facebook/lexical/blob/v0.49.0/packages/lexical/src/LexicalEvents.ts#L1605-L1655); [rich-text key handlers](https://github.com/facebook/lexical/blob/v0.49.0/packages/lexical-rich-text/src/index.ts#L1522-L1633))
- rich-text registrations implement the commands against the current selection and handle paste through the clipboard pipeline; and ([rich-text commands](https://github.com/facebook/lexical/blob/v0.49.0/packages/lexical-rich-text/src/index.ts#L1155-L1303); [rich-text clipboard commands](https://github.com/facebook/lexical/blob/v0.49.0/packages/lexical-rich-text/src/index.ts#L1759-L1803))
- `CONTROLLED_TEXT_INSERTION_COMMAND` can carry either a string or the original `InputEvent`, whose `dataTransfer` is significant for replacement/drop routes. ([Lexical command types](https://github.com/facebook/lexical/blob/v0.49.0/packages/lexical/src/LexicalCommands.ts#L39-L96); [rich-text controlled insertion](https://github.com/facebook/lexical/blob/v0.49.0/packages/lexical-rich-text/src/index.ts#L1194-L1221))

Therefore version 3 should intercept the semantic command once and expose the same internal proposal operation to toolbar and programmatic callers. It should use `BEFORE_INPUT_COMMAND` only where the original event carries target/data information not preserved by a higher command, and it must prevent duplicate capture when both key and `beforeinput` routes occur.

The current implementation does the opposite in several places: it separately handles `BEFORE_INPUT_COMMAND`, key Backspace/Delete, key Enter, and the downstream commands; it only handles `insertText`/`insertTranspose` in `beforeinput`; and when controlled insertion carries an event it reads `event.data` but not `dataTransfer`. ([current registration](https://github.com/mahendrimd/lexical-review/blob/56981eb3a52b33a38eeaae48763fa49aecc6ec03/packages/lexical-review/src/registerReviewText.ts#L235-L349)) These are v2 implementation observations, not recommended v3 behavior.

### Selection is the semantic input; DOM ranges and node keys are adapters

Lexical's `RangeSelection.insertText()` first removes a non-collapsed selection, preserves the first selected node's format/style, and then inserts; `formatText()` computes a toggle from the selection's aggregate format; `insertParagraph()` removes selected text and splits the containing block; and `deleteCharacter()` can extend a collapsed selection or merge blocks. ([text insertion](https://github.com/facebook/lexical/blob/v0.49.0/packages/lexical/src/LexicalSelection.ts#L887-L1062); [formatting](https://github.com/facebook/lexical/blob/v0.49.0/packages/lexical/src/LexicalSelection.ts#L2213-L2240); [paragraph insertion](https://github.com/facebook/lexical/blob/v0.49.0/packages/lexical/src/LexicalSelection.ts#L1355-L1393); [deletion](https://github.com/facebook/lexical/blob/v0.49.0/packages/lexical/src/LexicalSelection.ts#L1682-L1900))

Version 3 should snapshot the accepted-state semantic target and effective formatting before mutating the overlay. Lexical node keys and DOM ranges are ephemeral implementation attachments; portable proposal IDs, paragraph IDs, and offsets are distinct. A node transform after arbitrary mutation cannot reliably recover whether the intent was insertion, atomic replacement, format toggle, paste, or a compound command.

The current `ReviewTextNode` has only `original`, `insertion`, and `deletion` flags, and normalization merges adjacent nodes solely when those flags match. That rendering segmentation cannot preserve proposal identity or atomic boundaries. ([current node model](https://github.com/mahendrimd/lexical-review/blob/56981eb3a52b33a38eeaae48763fa49aecc6ec03/packages/lexical-review/src/ReviewTextNode.ts#L28-L63); [current normalization](https://github.com/mahendrimd/lexical-review/blob/56981eb3a52b33a38eeaae48763fa49aecc6ec03/packages/lexical-review/src/registerReviewText.ts#L47-L99))

### Deletion granularity belongs to Lexical/platform semantics

Input Events permits backward/forward deletion to remove different code-point or grapheme extents depending on platform and script, and `getTargetRanges()` identifies what the browser expects to replace. Lexical adds its own Unicode, segmented-node, decorator, block, and platform handling. ([Input Events deletion note](https://www.w3.org/TR/2026/WD-input-events-2-20260501/#interface-InputEvent-Attributes); [Lexical deletion](https://github.com/facebook/lexical/blob/v0.49.0/packages/lexical/src/LexicalSelection.ts#L1682-L1996))

Version 3 should create the proposal from the range resolved by Lexical/browser intent, validating the resulting UTF-16 endpoints against v1. It should not reimplement character and word expansion with `Selection.modify()`. The current `$markForDelete()` does exactly that and contains a known paragraph-start TODO, which makes it evidence for replacement rather than a v3 contract. ([current deletion implementation](https://github.com/mahendrimd/lexical-review/blob/56981eb3a52b33a38eeaae48763fa49aecc6ec03/packages/lexical-review/src/ReviewSelection.ts#L160-L171))

### IME must remain owned by Lexical during composition

Input Events makes `insertCompositionText` non-cancelable and describes repeated replacement of the active composition passage. Lexical returns early for composition `beforeinput`, reconciles DOM changes, contains special paths for Android and iOS Korean input, and preserves DOM node identity while composing. ([Input Events composition](https://www.w3.org/TR/2026/WD-input-events-2-20260501/#input-event-order-during-composition); [Lexical composition and mobile deletion](https://github.com/facebook/lexical/blob/v0.49.0/packages/lexical/src/LexicalEvents.ts#L815-L977); [Lexical selection composition path](https://github.com/facebook/lexical/blob/v0.49.0/packages/lexical/src/LexicalSelection.ts#L892-L927))

The v3 plugin should capture the pre-composition accepted selection, let Lexical/browser composition proceed, then diff/validate the committed semantic result and publish one `insert` or same-paragraph `replace` proposal. Cancellation publishes nothing. Composition over unsupported pending or multi-paragraph content should fail before composition where possible or restore atomically after commit; it must never emit partially committed proposal state.

## Recommended version 3 interaction contract

The following recommendations are lexical-review decisions constrained by the evidence. They are not assertions that every vendor behaves this way.

### Command and API boundary

1. Introduce one internal **proposal-intent service** that accepts an accepted-state target, the intended change, creator/source metadata, and an interaction-group context.
2. Route Lexical's standard semantic commands through it: controlled insertion, remove/delete character/word/line, paragraph insertion, and format/set-format for the four core properties. Paste/cut and composition adapt their rich event data into the same intents.
3. Expose a public programmatic API over the same service. A host toolbar, keyboard route, automation, and AI caller must obtain the same proposal semantics for the same explicit intent.
4. In review mode, refuse or leave disabled any content-mutating command that has not declared a proposal integration. CKEditor likewise disables commands that have not been prepared for track changes, rather than allowing untracked mutation. ([CKEditor custom command integration](https://ckeditor.com/docs/ckeditor5/latest/features/collaboration/track-changes/track-changes-custom-features.html#enabling-commands))
5. Do not promise that arbitrary `editor.update()` mutations become proposals. Provide an explicit escape hatch for loading accepted state and an explicit proposal API for host transformations.

### Gesture-to-proposal rules for the conforming first slice

| ------------------------------------------------------------------------------------------------------------------- | --------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Type/insert committed non-empty text at a collapsed caret in one paragraph                                          | `insert`              | Carry exact effective formatting. Coalescing multiple typing intentions requires the authoring-session decision below.                  |
| Backspace/Delete/word/line delete resolving to a non-empty range inside one paragraph                               | `delete`              | Use Lexical/browser-resolved range, exact text, and effective formatting; forward/backward affects target discovery, not proposal kind. |
| Type, paste, autocorrect, or programmatically replace one non-empty accepted range inside one paragraph             | `replace`             | One user/programmatic intent becomes one atomic v1 proposal, even though CKEditor and document formats may use separate native units.   |
| Toggle/set a core format on one non-empty accepted range with one uniform `before` value                            | `format`              | Record explicit Boolean before/after. The UI route does not matter.                                                                     |
| Toggle/set formatting at a collapsed caret                                                                          | no immediate proposal | Update typing state; the next insertion's content fragment records effective formatting.                                                |
| Press Enter at a collapsed point in a supported paragraph                                                           | `paragraph-split`     | Reserve the right paragraph ID; preserve the left ID as v1 requires.                                                                    |
| Backspace at paragraph start or Delete at paragraph end when Lexical resolves an adjacent supported paragraph merge | `paragraph-merge`     | The direction selects the boundary; v1's result still retains the left paragraph ID.                                                    |
| Accept/reject one ID or a compatible set                                                                            | v1 atomic resolution  | Validate and remap before mutation. An empty/failed transaction makes no content, lifecycle, or selection change.                       |

These rules require a preflight step before the visible editor mutation, plus rollback or a non-editable refusal for unsupported targets.

### Predictable first-slice refusals

Unless the standard is amended first, version 3 should refuse with a typed reason and leave content/proposals unchanged for:

- selection replacement or deletion spanning more than one accepted paragraph;
- multiline paste that inserts paragraph boundaries;
- Enter over a non-collapsed selection when it combines replacement/deletion with split;
- formatting across paragraphs or a range whose selected text does not have one uniform required `before` value, unless the product explicitly accepts independently resolvable per-range proposals;
- an edit whose target intersects pending inserted/deleted/formatted content and cannot be represented against accepted state alone;
- insertion of a soft line break until an exact mapping between Lexical's `LineBreakNode` and accepted paragraph text is specified;
- unsupported rich clipboard structure; and
- arbitrary custom commands without a proposal adapter.

Refusal is not the desired long-term UX. It is the honest v3-v1 conformance boundary until adoption feedback produces a compound-proposal, proposal-authoring, or richer-content rule.

### Clipboard policy

The package should distinguish three operations:

1. **Ordinary copy:** export either the accepted/final or rejected/original content projection as `text/plain` and supported `text/html`, selected by an explicit host policy. No proposal identity is implied.
2. **Proposal-preserving copy/export:** use an explicit typed/internal payload or Web Editor Revisions document with identity, base, targets, and loss reporting. It is not inferred from `<ins>`, `<del>`, or generic rich HTML.
3. **Paste:** parse supported rich/plain content into one insertion or same-paragraph replacement intent. Do not trust foreign suggestion markup as native proposals. Multiline or unsupported structure follows typed refusal until compound behavior is specified.

Cut combines the chosen copy projection with a delete proposal against accepted content. It must not silently remove accepted text. Cutting pending content is part of the unresolved proposal-authoring policy.

### Resolution and navigation

The semantic API should resolve by proposal ID, not by whichever DOM marker or caret is active. The demo may offer current, selected, and all controls because those patterns recur, but “all” should pass an explicit compatible ID set into the same atomic resolver. Preview modes should calculate projections without changing lifecycle.

The package still needs a deterministic **post-resolution selection** rule. Primary sources show navigation to next/previous changes and sometimes automatically move after resolution, but do not define a shared caret rule. A separate decision should specify whether the selection follows a remapped semantic point, collapses to the resolved change start, advances to the next proposal, or remains UI-owned.

## Web Editor Revisions v1 adoption findings

These are feedback candidates, not proven specification defects. Each needs an isolated fixture and a decision in the sibling repository before changing v1.

### A. Proposal authoring lifecycle

**Reproduction:** Enable review mode, type `abc`, then Backspace once before any review decision or export. Products ordinarily let the author correct the insertion; CKEditor also expands adjacent suggestions and exposes updates to suggestion data. ([CKEditor granularity](https://ckeditor.com/docs/ckeditor5/latest/features/collaboration/track-changes/track-changes-granular-suggestions.html); [CKEditor integration](https://ckeditor.com/docs/ckeditor5/latest/features/collaboration/track-changes/track-changes-integration.html))

**V1 tension:** shrinking the insertion changes its immutable payload; deleting and recreating it reuses neither identity nor lifecycle; a delete proposal cannot target the inserted content; withdrawal is excluded. ([v1 target and identity](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L153-L200))

**Question for the standard:** Is there a non-portable “draft proposal” phase before a proposal enters the interchange document, a replace/supersede relation, or a versioned withdrawal/amendment operation? Define exactly when identity becomes immutable.

### B. Interaction grouping versus proposal identity

**Reproduction:** Type adjacent characters, pause, move the caret away and back, then continue typing. CKEditor uses same-user adjacency by default and allows a new tracking session to stop joining. ([CKEditor granularity](https://ckeditor.com/docs/ckeditor5/latest/features/collaboration/track-changes/track-changes-granular-suggestions.html))

**V1 tension:** v1 defines independently resolvable proposal identity and same-point order, but not capture sessions, presentation groups, or whether adjacent authoring events are one proposal.

**Question for lexical-review first:** Should v3 emit immutable proposal-per-intent records and group them only in UI, or keep an unpublished authoring transaction open until a deterministic boundary? Only the latter creates pressure for a standard drafting rule.

### C. Compound multi-paragraph changes

**Reproduction:** Select the last word of paragraph A through the first word of paragraph B and type replacement text, or paste two paragraphs over a same-paragraph selection.

**V1 tension:** the action needs paragraph-local text changes plus a boundary change, with shared atomic resolution. V1 has the primitive kinds but forbids dependencies and cross-paragraph text ranges. ([v1 targets and compatibility](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L153-L167); [v1 selective resolution](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L262-L280))

**Question for the standard:** Add an atomic compound proposal/group with dependent child transformations, broaden targets, or explicitly keep these interactions outside the portable core. This is the largest practical coverage gap for a normal text editor.

### D. Mixed-format selection

**Reproduction:** Select one bold and one non-bold accepted run, then issue the standard bold toggle. Lexical computes one aligned target format from the selection, but v1 requires one uniform `before` value across a formatting proposal. ([Lexical format toggle](https://github.com/facebook/lexical/blob/v0.49.0/packages/lexical/src/LexicalSelection.ts#L2213-L2240); [v1 formatting](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L240-L244))

**Question:** Is independently resolvable proposal-per-uniform-run acceptable, or does one formatting command need an atomic multi-range/compound proposal? Until decided, version 3 should refuse the mixed-before case in its conforming mode.

### E. Clipboard projection vocabulary

CKEditor demonstrates that retaining suggestions and copying an accepted projection are both legitimate policies. V1 defines accepted and rejected document projections but no clipboard API or projection selector. ([CKEditor clipboard](https://ckeditor.com/docs/ckeditor5/latest/features/collaboration/track-changes/track-changes.html#clipboard-integration); [v1 excluded browser API](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L60-L77))

This is initially a lexical-review policy, not necessarily a v1 defect. It becomes standard feedback only if a portable clipboard profile or fragment interchange document is desired.

## Required demo and test evidence

The rewritten demo should be an executable capability surface, not the normative source. At least one editor should work with no toolbar using native typing, selection, deletion, Enter, paste, IME, and keyboard formatting. A second configuration may add toolbar and proposal-list controls that dispatch the same commands/APIs. The demo should show accepted/original projection previews, individual/compatible-set resolution, interchange import/export, and typed unsupported outcomes.

The implementation plan should require fixtures across these dimensions:

| Dimension     | Minimum cases                                                                                                                                   |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Input route   | physical key, `beforeinput`, toolbar command, direct Lexical command, public proposal API                                                       |
| Selection     | collapsed start/middle/end, forward/backward same-paragraph range, exact paragraph boundary, unsupported cross-paragraph range                  |
| Text          | ASCII, non-BMP code point, combining sequence, word deletion, autocorrect/`insertReplacementText`                                               |
| Formatting    | each core format add/remove, collapsed typing format, mixed-before refusal, formatting within pending insertion policy                          |
| Clipboard     | plain and supported rich paste, replacement paste, empty data, multiline refusal, explicit projection copy, cut                                 |
| Composition   | commit and cancel, collapsed insertion and same-paragraph replacement, Android/iOS/Safari/Firefox paths proportionate to Lexical's source risks |
| Paragraph     | split at start/middle/end, merge backward/forward, empty paragraphs, selection-plus-Enter refusal                                               |
| Pending state | target next to pending proposal, target intersecting pending insertion/deletion/format, author correction policy                                |
| Resolution    | accept/reject each kind, compatible batch, failed atomic preflight, surviving target remap, deterministic post-resolution selection             |
| Interchange   | producer/consumer/resolver conformance fixtures for all six kinds plus adoption-finding fixtures that are expected refusals                     |

Browser tests are required where the route depends on native selection, clipboard, composition, or `beforeinput`; jsdom command tests alone cannot establish those behaviors. Lexical's own source contains browser- and platform-specific branches for these surfaces, including iOS key deferral, Android deletion, Safari line-break inference, Firefox clipboard/input handling, and non-cancelable composition. ([Lexical event routing](https://github.com/facebook/lexical/blob/v0.49.0/packages/lexical/src/LexicalEvents.ts#L815-L1180); [rich-text key handlers](https://github.com/facebook/lexical/blob/v0.49.0/packages/lexical-rich-text/src/index.ts#L1522-L1633))

## Decisions this evidence enables

The evidence is strong enough to constrain later architecture tickets as follows:

- proposal records and presentation segments must be separate concepts;
- the proposal service sits below keyboard/toolbar/AI routes and above Lexical mutations;
- the standard's six kinds determine the first conforming semantic slice;
- one same-paragraph replacement intent is atomic even though vendors may serialize two changes;
- paragraph split/merge classification follows the resolved Lexical structural intent, not a raw key or `inputType` alone;
- composition commits one intent after Lexical reconciliation;
- ordinary clipboard content and proposal-preserving interchange are separate;
- arbitrary custom commands do not receive implicit conformance; and
- unsupported compound or pending-on-pending edits are typed refusals until their adoption findings are decided.

The remaining decisions are product/architecture questions rather than missing research:

1. where the native proposal store lives relative to Lexical nodes and Web Editor Revisions documents;
2. whether an unpublished authoring transaction exists and what closes it;
3. whether to seek a standard amendment for compound proposals before v3 or ship explicit first-slice refusals;
4. the default ordinary-copy projection;
5. post-resolution caret/selection behavior; and
6. how proposal groups are exposed without weakening independent resolution or immutable identity.

## Limitations

First-party product documentation rarely specifies exact caret locations, event sequences, IME behavior, paragraph-boundary proposal grouping, or the handling of edits inside another pending change. Absence from documentation is recorded as a gap, not evidence of absence. No live signed-in vendor editor experiment was used, because such an experiment would be a product observation rather than a stable primary-source contract unless paired with a pinned version and reproducible fixture.

Input Events Level 2 is a W3C Working Draft, not a browser-conformance guarantee, and it explicitly notes both incomplete implementation reporting and platform variance. It is useful as an intention vocabulary and as evidence against key-specific semantics, not as proof that every browser supplies the same events. ([Input Events status and problems solved](https://www.w3.org/TR/2026/WD-input-events-2-20260501/))

Vendor observations in this note are inspiration and counterevidence. The recommended lexical-review decisions are the deterministic contract proposed for v3, bounded by Web Editor Revisions v1 and exact Lexical 0.49 semantics; they do not claim compatibility with Word, Google Docs, CKEditor, or ONLYOFFICE.
