# Web Editor Revisions v1 conformance boundary for `lexical-review` v3

## Question and answer

Which Web Editor Revisions v1 roles can `lexical-review` v3 claim directly, and when does it need a mapping profile and adapter claim?

`lexical-review` v3 can directly claim the **core interchange document**, **producer**, **consumer**, and **resolver** roles at a public Web Editor Revisions JSON API boundary. Those roles constrain portable artifacts and observable resolution behavior; the standard explicitly does not standardize runtime data structures, editor UI, DOM shape, or private persistence, and it makes conformance role- and boundary-specific. A conforming producer emits canonical documents/bytes, a consumer validates before relying on them, and a resolver implements exact projections and remapping for every claimed proposal kind. ([standard §§1, 3, 15](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L7-L88), [role requirements](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L478-L510))

A **mapping-adapter** claim is additionally required when the project claims that an import, export, save/reload, persistence, or other declared adapter boundary is semantically equivalent to the core—for example, import from persisted Lexical editor JSON, export back to that JSON, save/reload of the live editor plus any proposal sidecar, or a separately claimed storage round trip. Such a claim must name a profile and version, direction, supported proposal kinds, exact measured boundary, and mapping reports. Named source systems use independently versioned profiles; the existing Reference Web Editor profile is pinned to CKEditor 5 v48.3.1 and therefore cannot be reused for Lexical. ([standard §§14.1, 14.4, 15.5, 16](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L353-L379), [bounded equivalence](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L464-L476), [profiles](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L529-L543), [Reference Web Editor boundary](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/profiles/reference-web-editor.md#L13-L41))

The cleanest v3 boundary is therefore:

1. make a Web Editor Revisions v1 document (or an isomorphic in-memory value) the authoritative portable review model;
2. expose its validator, canonical serializer, importer/exporter, proposal creation API, and pure resolver from a React-free package boundary;
3. treat Lexical nodes and DOM as a projection/editor integration, not as the interchange document; and
4. defer a `lexical-review` mapping profile unless v3 promises interchange equivalence for Lexical editor JSON or another native persistence representation.

This is an architectural inference from the role definitions and the rule that internal object layout is non-normative. It avoids inventing mapping reports for ordinary in-process rendering while leaving a precise route to a future Lexical persistence claim. ([canonical serialization](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L297-L347), [role-specific evaluation](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L478-L527))

## Role and claim matrix

| v3 capability | Direct core claim | Mapping profile needed? | Claim boundary |
| --- | --- | --- | --- |
| Parse and validate Web Editor Revisions v1 JSON | Consumer | No | bytes/value → validated core document |
| Emit a schema- and semantics-valid core document and exact JCS bytes | Producer (and conforming document) | No | authoritative core model → canonical bytes |
| Accept/reject one or more compatible proposals with exact successor state | Resolver for the six claimed kinds | No | verified core document + resolution request → successor core document |
| Emit canonical bytes and later parse those supplied bytes, without claiming the intervening storage system | Producer + consumer | No | separate canonical serialization and parsing API boundaries |
| Claim preservation through a storage save/reload boundary, even when storing canonical core bytes | Mapping adapter/persistence operation in addition to producer + consumer | Yes; scope it narrowly to the storage identity mapping | canonical core bytes → named storage/configuration → reloaded core bytes |
| Render/edit the authoritative core model through transient Lexical nodes | No separate standard role; editor behavior is outside v1 | No, unless equivalence of a Lexical-native artifact is claimed | package behavior/tests, not a portable-format claim |
| Import persisted Lexical editor state as core | Mapping adapter, Lexical-to-core | Yes | pinned Lexical/package/config/source state → core document |
| Export core to persisted Lexical editor state or a Lexical-plus-sidecar format | Mapping adapter, core-to-Lexical | Yes | core document → pinned persisted native boundary after reload |
| Claim bidirectional Lexical-native round trips | Two direction-specific mapping claims | Yes | one claim manifest/evidence package per direction |

The standard limits each mapping equivalence claim to one operation, direction, profile/version, inputs/outputs, and measured boundary; a bidirectional adapter consequently needs at least two claims. ([standard §14.4](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L464-L476), [evaluation claim rules](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/evaluation/README.md#L57-L63))

## Why the v2 model cannot itself be the conforming core

The published v2 node stores only a numeric review segment state corresponding to `original`, `insertion`, or `deletion`; its JSON adds one `review` field to Lexical's serialized text node. Adjacent nodes with the same review state are normalized together. It has no independent proposal identifier, base fingerprint, target association, `samePointOrder`, lifecycle, provenance, atomic replacement relation, formatting proposal payload, or paragraph-boundary proposal record. ([current review representation](https://github.com/mahendrimd/lexical-review/blob/56981eb3a52b33a38eeaae48763fa49aecc6ec03/packages/lexical-review/src/ReviewTextNode.ts#L30-L53), [serialization](https://github.com/mahendrimd/lexical-review/blob/56981eb3a52b33a38eeaae48763fa49aecc6ec03/packages/lexical-review/src/ReviewTextNode.ts#L260-L290), [export](https://github.com/mahendrimd/lexical-review/blob/56981eb3a52b33a38eeaae48763fa49aecc6ec03/packages/lexical-review/src/ReviewTextNode.ts#L440-L476), [normalization](https://github.com/mahendrimd/lexical-review/blob/56981eb3a52b33a38eeaae48763fa49aecc6ec03/packages/lexical-review/src/registerReviewText.ts#L34-L84))

Selection replacement in v2 marks the selected content for deletion and then inserts text, so it is visually a replacement but not the one independently resolvable atomic `replace` proposal required by v1. Paragraph insertion delegates directly to Lexical and does not create a paragraph-split proposal. ([replacement editing path](https://github.com/mahendrimd/lexical-review/blob/56981eb3a52b33a38eeaae48763fa49aecc6ec03/packages/lexical-review/src/ReviewSelection.ts#L233-L278), [paragraph command](https://github.com/mahendrimd/lexical-review/blob/56981eb3a52b33a38eeaae48763fa49aecc6ec03/packages/lexical-review/src/registerReviewText.ts#L116-L127), [replacement semantics](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L232-L238))

Consequently, v3 needs a proposal store/model separate from presentation-oriented review segments. `ReviewTextNode` may remain a projection primitive, but segment boundaries cannot be proposal identity. This is a design consequence, not a conformance requirement on Lexical's runtime layout.

## Exact evidence required for the six-kind core claim

All six kinds share these release-gate requirements:

- Schema plus semantic validation, strict duplicate-member detection, the narrow JSON profile, canonical proposal sorting, exact RFC 8785 JCS bytes, and accepted-state SHA-256 fingerprint comparison. ([standard §§5, 12, 15.1–15.3](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L109-L127), [serialization](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L297-L347), [roles](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L482-L502))
- Exact acceptance and rejection projections for every claimed kind, mixed selective resolution, rejected-only resolution, verified successor fingerprints, deterministic remapping of every unselected pending target, and proof that every preflight failure leaves content, lifecycle, fingerprint, and targets unchanged. ([standard §§10–11](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L262-L295))
- UTF-16 offsets tested with non-BMP text, invalid surrogate-splitting offsets rejected, exact text preserved without normalization, and formatting fragments carried with text. ([standard §§6.2, 9](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L132-L151), [content fragments](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L212-L220))
- Proposal identity stability through serialization and remapping; either omit terminal proposals or retain the complete original record. For v3, omitting terminal records is the safer initial conforming choice because the published oracle has a terminal-validation defect described below. ([standard §8](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L169-L210))

| Kind | Positive acceptance/rejection evidence | Validation and atomicity evidence | Successor/remapping evidence |
| --- | --- | --- | --- |
| `insert` | Exact non-empty text and complete explicit formatting splice on accept; accepted state unchanged on reject | Valid point/code-point boundary; unique `samePointOrder` per base point + association; canonical ordering independent of proposal ID/array order/time/provenance | Later offsets shift by UTF-16 length; `before`/`after` attachment is exact; co-located insertions remain in ascending `samePointOrder` even when accepted in separate selective transactions |
| `delete` | Exact targeted text and formatting removed on accept and preserved on reject | Non-empty range; payload exactly equals base fragment including formatting; mismatch and target-inside-consumed-content cases refuse before mutation | Later offsets shift left; targets inside removed content are rejected as incompatible/unmappable, never guessed |
| `replace` | One atomic remove+insert on accept; exact old content on reject | Non-empty matching `oldContent` and non-empty `newContent`; never inferred from adjacent insertion/deletion; cannot resolve children independently | Apply delete+insert remapping atomically using the new fragment length, including boundary associations |
| `format` | All named properties apply their `after` values atomically on accept and preserve `before` values on reject | Non-empty range/map; every `before` value uniform across the target and differs from `after`; exercise bold, italic, underline, strikethrough, removal, and multi-property atomic proposals | Text coordinates do not move; formatting coverage remains a normalized complete partition and follows later text edits |
| `paragraph-split` | Accept at offset 0, middle, and paragraph length; left keeps its identity, collision-free right ID is created, suffix text/formatting moves exactly; reject preserves one paragraph | Valid point and `newRightParagraphId`; collision and incompatible structural transactions fail without mutation | Suffix targets move to right-relative offsets; at split point `before` becomes left end and `after` becomes right start; a range that would cross the split is incompatible |
| `paragraph-merge` | Accept ordinary and empty-paragraph cases; concatenate exact text/formatting, retain left identity, retire right; reject preserves both | Boundary names adjacent paragraphs in order; non-adjacent and incompatible structural transactions fail without mutation | Right-paragraph targets move to left by adding the pre-merge left UTF-16 length; left targets remain attached |

These observations are the direct expansion of the kind semantics and resolver requirements. ([proposal kinds](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L218-L260), [resolution/remapping](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L262-L295))

The publication runner currently has 13 internally registered fixture groups covering canonical insertion, strict JSON, fingerprint projection, text operations, formatting, structural operations, same-point ordering, operation-specific remapping, identity/terminal retention, semantic invalid cases, normalized semantics, mapping outcome vocabularies, and invalid loss reporting. Its literal external fixture contains only one insertion document; the remaining cases are constructed inside Python. ([evaluation README](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/evaluation/README.md#L12-L35), [registered fixtures](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/evaluation/run_conformance.py#L758-L883))

For a defensible v3 claim, retain this evidence in CI/release artifacts:

1. package-native black-box tests of the public TypeScript producer, consumer, and resolver APIs for every row above;
2. the exact standard publication commit (`e6ac89287257646888a4eadf692d836eb8feb41b`), implementation commit/version, Node/OS/runtime details, commands, and full logs;
3. hashes of the normative schema and literal serialization fixture (at the researched commit: schema `fbdf4ba97b05c97d7ada1b1437a8e6fc0fbc234485bb15282ef3750df243de02`; fixture `6d986605b3463d00027e95bc2f7ef03c76997dac03f3db0ef033c84f7aff050b`);
4. cross-implementation comparison of canonical bytes, fingerprints, acceptance/rejection projections, and successor targets against independently encoded expected vectors; and
5. only claim roles and six kinds actually exercised, without implying vendor compatibility.

The publication itself asks claims to record the publication commit, environment, command, log, schema/fixture hashes, and to compare bytes and projections across encoders. It also warns that passing the core path does not exercise a native editor or document format. ([evaluation guidance](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/evaluation/README.md#L31-L39))

## First-adopter findings to report upstream

### 1. The “core evaluation” does not execute an adopter implementation

The documented command runs the publication's Python functions: `main()` iterates the file-local `TESTS` registry, and fixture builders call the same file's validator, serializer, and resolver. There is no implementation-under-test protocol, CLI contract, or portable expected-output vector corpus for a TypeScript adopter. Therefore “run the core suite against the publication commit used by the adapter” verifies the publication oracle, not `lexical-review`'s implementation. ([runner entry point](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/evaluation/run_conformance.py#L1074-L1098), [fixture registration](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/evaluation/run_conformance.py#L758-L775), [documented procedure](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/evaluation/README.md#L19-L35))

**Feedback:** publish language-neutral JSON vectors containing input document, resolution request, expected output/error, and expected canonical bytes for all 13 groups, or define an implementation adapter protocol that the runner invokes. Until then, `lexical-review` should port the oracle cases into black-box package tests and describe them as adopter evidence rather than saying the upstream script tested the package.

### 2. Selectively accepting a higher-order co-located insertion breaks the runner's required order

The standard requires co-located accepted fragments to appear in ascending `samePointOrder` and says both association and explicit insertion order determine successor attachment. The runner uses `samePointOrder` when simultaneous insertions are applied, but its successor offset transformation only receives the remaining target's `association`; it does not compare the accepted and pending insertion orders. Its fixture accepts orders 0 and 1 together and leaves order 2 pending, so it does not exercise accepting order 1 before order 0. ([normative ordering](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L218-L224), [normative remapping](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L282-L295), [runner transform](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/evaluation/run_conformance.py#L487-L531), [fixture](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/evaluation/run_conformance.py#L867-L879))

For base text `AB`, two `after` insertions `x` (order 0) and `y` (order 1), accepting `y` first moves pending `x` after `y` under the runner's association-only transform; later accepting `x` yields `AyxB`, contradicting the required ascending order `AxyB`.

**Feedback:** add selective-resolution vectors in both order directions and define/remedy the remap algorithm so the pending proposal's same-point relation survives materialization order.

### 3. Retained terminal records conflict with the runner's current-state validation

The standard permits retaining a complete terminal record with its **original** base fingerprint, target, kind, and payload, while explicitly not requiring the historical accepted-state snapshot. The runner correctly keeps the original record, then calls `validate_semantics()` on the successor document; that validator checks every proposal target and deletion/replacement payload against the **current** accepted state regardless of lifecycle. The only retention fixture uses insertion, whose point can remain valid by accident. Accepted deletion, replacement, split, and merge records can consequently fail validation after their targets/content have been materialized or paragraph identities retired. ([terminal record rule](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L189-L200), [unconditional target/payload validation](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/evaluation/run_conformance.py#L318-L385), [retention and successor validation](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/evaluation/run_conformance.py#L630-L650), [insertion-only fixture](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/evaluation/run_conformance.py#L923-L935))

**Feedback:** clarify lifecycle-sensitive semantic validation and add retained-terminal fixtures for every kind. The validator should validate terminal records structurally and for record completeness without treating their original targets/payloads as attached to the current accepted state. `lexical-review` v3 should omit terminal proposals until the erratum is resolved; an application can keep audit history outside the v1 interchange document.

### 4. Compatible multi-structural transactions are normatively allowed but rejected by the oracle

The normative resolver accepts any compatible transaction and only rules out overlapping, nested, or dependent proposals. The runner rejects every transaction containing more than one accepted split/merge, even when operations affect independent paragraphs, and no fixture covers this case. ([transaction rules](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L262-L280), [runner restriction](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/evaluation/run_conformance.py#L578-L587))

**Feedback:** either make the core model explicitly limit a transaction to one structural proposal (a semantic-version-impacting restriction) or extend the oracle with independent multi-split/merge cases and deterministic simultaneous application/remapping. A six-kind resolver claim should not copy this runner limitation silently.

## Decision for the v3 plan

- Plan direct v1 **producer, consumer, and resolver** claims for all six proposal kinds at the canonical core API boundary.
- Make the canonical core proposal model authoritative; keep Lexical nodes as an editor projection and let human, automation, and future AI integrations create the same proposal records through one general API.
- Do not claim that Lexical editor JSON, DOM, or another vendor format conforms or round-trips equivalently in v3.
- Do not create a Lexical mapping profile unless a later decision adds a native Lexical persistence/import-export promise. If added, define it in the standards repository, pin Lexical/package versions and configuration, specify both directions separately, and activate save/reload, rollback, partial-persistence, identity, six-kind, and report evidence following the profile procedure. ([profile evidence procedure](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/evaluation/README.md#L37-L63))
- Feed the four findings above to `web-editor-revisions` as reproducible adopter feedback before treating its executable oracle as a sufficient release gate. None requires `lexical-review` to silently reinterpret the standard: use the normative prose where clear, document the affected claim, and avoid the ambiguous retained-terminal option until corrected. The standard itself requires reporting apparent schema/prose conflicts rather than guessing and identifies failed independent projections and implementation feedback as reassessment triggers. ([conflict rule](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L39-L45), [reassessment triggers](https://github.com/mahendrimd/web-editor-revisions/blob/e6ac89287257646888a4eadf692d836eb8feb41b/standards/v1/standard.md#L555-L575))
