Throwaway prototype

One interaction contract, many noisy input routes

Drive candidate version 3 rules through proposal boundaries, local authoring, exported work, formatting, paragraphs, clipboard, IME, and preview projections. The prototype is a discussion tool, not production code or a public API draft.

Question being tested: Can one route-neutral semantic state machine make every in-scope review interaction deterministic while preserving accepted state, pending work, projection, and logical selection on every refusal?
Candidate answer: Browser events, Lexical commands, toolbar actions, clipboard actions, IME sessions, and programmatic calls first normalize into one semantic intent. That service decides from the accepted-state target, proposal intersection, local draft, composition phase, and projection. Raw browser event order never changes the normative outcome.
Evidence boundary: The repository resolves Lexical 0.49.0. Its tagged source contains different Android Chrome, Firefox, Safari/WebKit, and iOS composition/deletion paths. Those facts justify adapter-specific normalization and browser conformance tests; they do not define Lexical Review semantics. Vendor observations are likewise informative, never normative.

      Assumptions deliberately exposed for review

      • Candidate A caret adjacent to exported work must carry an accepted-side association. The service supports an action only when that association makes the accepted target unique; an ambiguous visual boundary refuses.
      • Candidate Continuous text authoring—insert, delete, replace, paste, and IME—uses a mutable local draft. Complete discrete intentions—format, split, and merge—create immutable proposals immediately.
      • Candidate Active composition is a semantic critical section. Export and proposal resolution refuse until commit or cancel; interim DOM variation is adapter-local.
      • Candidate A formatting adapter resolves “toggle” into an explicit desired value before calling the semantic service. A collapsed toggle only changes future local input formatting and creates no proposal by itself.
      • Candidate Review-changing edits run only in the review projection. Projection previews are read-only, but explicit accept/reject remains available because it acts on the authoritative proposal ledger rather than preview content.
      • Candidate If an adapter cannot normalize or roll back a browser mutation safely, it reports an operational failure and rebuilds from authoritative state; it never invents different review semantics for that browser.
