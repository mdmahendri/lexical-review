Can one review document carry a million pending proposals?

This throwaway benchmark explores which version 3 scalability constraints belong in the specification. It exercises a candidate indexed review-state representation; it is not the version 3 implementation or serialization schema.

The question. Can adding and finalizing a draft near the beginning, reconciling a relevant projection, native load/save, and WER v1 export remain predictable with up to 1,000,000 independently pending proposals, while proposal-only changes reuse the accepted-state fingerprint?
What this can and cannot prove. Relative growth and main-thread isolation are meaningful here. Absolute timings and heap figures describe this browser and this candidate shape only. The million-proposal run is intentionally heavy; serialization temporarily retains a large JSON string in memory.
Local work is local

Draft finalization and relevant projection cost should not grow with the total proposal count.

Global work says so

Native load/save and WER export may be linear, but must remain outside the editor's interactive path.

Accepted content is stable

Proposal-only changes and WER export read, but never rebuild, the accepted-state fingerprint.

Evidence before ceilings

Memory and throughput ceilings remain open until the million-proposal run produces evidence.

Free play

Every operation runs in a worker so the page remains responsive. Start small, then repeat with one million proposals.

Serialization boundaries

Native save materializes candidate JSON so native load can parse it. WER export generates exact per-proposal JSON but counts bytes instead of retaining the whole export; native atomic document-fragment insertions are reported as unsupported.

Decision prompts

  • Should v3 require p95 draft finalization and relevant reconciliation within one 16 ms frame at one million proposals?
  • Should native load/save and WER export be specified as linear, asynchronous, cancellable work with progress reporting instead of given a device-specific time ceiling?
  • What heap and serialized-size ceiling is acceptable for the million-proposal release gate?
  • Does the native JSON peak justify a streaming or chunked serialization seam in the public API?
